# 04 · RAGFlow PoC 实施与评测

> 对应 FDE 流程的**原型 + 验证**阶段。目标：用真实文档和真实并发，在 2~3 天内回答“RAGFlow 能不能替代现在的检索内核”。

## 1. PoC 目标与非目标

**目标**
- 验证中文 PDF/Word/PPT/Excel/扫描件的解析质量。
- 验证混合检索、重排、引用是否满足业务。
- 验证增量新增/更新/删除。
- 验证 API 能否被 BFF 集成。
- 压测 10/30/100 并发，确认检索层不再是瓶颈。

**非目标**
- 不做完整权限/多租户（PoC 只验证可行性）。
- 不迁移全部知识库。
- 不追求最终 UI。

## 2. 前置条件

| 项 | 要求 |
|---|---|
| 服务器 | Linux x86_64，16 vCPU / 32GB（64GB 更稳），100GB+ SSD |
| Docker | Docker 24+，Docker Compose v2 |
| 网络 | 内网；能访问内部镜像仓库；如需拉取官方镜像，提前离线导入 |
| 模型 | 内部 LLM 网关（OpenAI/Anthropic 兼容）；本地 embedding/rerank 模型或网关 |
| 数据 | 一个演示库（建议先用脱敏/公开文档，不要一上来用客户资料） |
| 账号 | 服务器 sudo、Docker 权限、域名/端口 |

先跑环境自检：

```bash
python tools/ragflow_poc/check_env.py
```

## 3. 实施步骤

### 3.1 安装与启动
1. 安装 Docker/Compose；配置镜像加速或离线镜像。
2. 获取 RAGFlow 官方 Docker Compose（以官方仓库当前版本为准），**固定版本号**。
3. 修改 `.env`：
   - Web/API 端口只监听内网或放在 Nginx 后面；
   - 数据库/MinIO/Redis 密码改成强密码；
   - LLM 指向内部网关；
   - embedding/rerank 模型路径或服务地址；
   - 关闭不需要的公网回调。
4. 启动并检查：
   - `docker compose ps` 全部 healthy；
   - Web 控制台可登录；
   - API 健康检查通过。

### 3.2 导入一个知识库
1. 新建 dataset，命名带项目前缀（如 `poc-demo`）。
2. 上传 20~50 份代表性文档：PDF、Word、PPT、Excel、扫描件各几份。
3. 观察解析结果：段落、表格、图片、页眉页脚、乱码、OCR。
4. 记录失败文件和原因。

### 3.3 API 冒烟
以部署版本的官方 API 文档为准，至少验证：
- 创建/列出 dataset；
- 上传文档、触发解析、查询状态；
- 检索（返回 chunk、score、文档定位）；
- 对话/流式回答（SSE）；
- 删除文档后不再被检索到；
- 更新文档后返回新内容。

> 不要凭记忆写 HTTP 路径；用官方 OpenAPI/控制台“开发者工具”确认。

### 3.4 评测（20~50 题）
- 从真实问题里选 20~50 条，标注应命中的文件和关键词。
- 指标：Recall@k、MRR、引用准确率、回答正确率、拒答正确率。
- 方法见 `05-评测与压测方法.md`（或本文第 6 节）。
- 对比现有系统；记录每条失败原因。

### 3.5 压测（10/30/100）
- 用现有 `tools/loadtest/` 的假大模型隔离上游；把 BFF 的检索适配到 RAGFlow。
- 观察：
  - 检索/重排 P95；
  - RAGFlow worker/ES CPU、内存；
  - 错误率、队列；
  - 应用层 P95。
- 目标：检索 P95 < 500ms，重排 P95 < 1s，应用层 P95 < 5s（不含 LLM）。

## 4. 验收表

| 类别 | 检查项 | 通过标准 |
|---|---|---|
| 解析 | 中文 PDF/Word/PPT/Excel | 主要段落、表格可读，无大面积乱码 |
| 解析 | 扫描件/图片 | OCR 可读，关键字段可检索 |
| 检索 | 单跳事实题 | Recall@8 ≥ 0.85（按业务调整） |
| 检索 | 表格/清单题 | 能命中对应文件/页 |
| 检索 | 多跳/综合题 | 至少命中 1 个关键来源 |
| 生成 | 引用 | 答案能定位到文件/片段 |
| 生成 | 拒答 | 库内没有时明确说不知道 |
| 增量 | 新增 | 5 分钟内可被检索 |
| 增量 | 更新 | 旧内容不再返回 |
| 增量 | 删除 | 不再被检索 |
| API | 流式 | SSE 逐段返回，不被缓冲 |
| API | 权限 | 越权 dataset 返回 403 |
| 性能 | 10/30 并发 | 无错误，P95 达标 |
| 性能 | 100 并发 | 有排队/429，不雪崩；P95 可接受 |
| 资源 | CPU/内存 | 峰值不超过服务器 80% |
| 运维 | 重启/恢复 | 数据不丢，可自动拉起 |
| 安全 | 默认口令/端口 | 已改密码，端口不暴露公网 |

## 6. 评测与压测方法（摘要）

**评测集设计**
- 50~100 题，覆盖：项目认知、部署步骤、环境信息、表格/清单、故障排查、库外问题（拒答）。
- 每题标注：标准答案要点、应命中文件、关键词、难度。
- 每次改检索/模型/切块都跑同一套；结果存档。

**指标**
- 检索：Recall@k、MRR、命中文件准确率。
- 生成：要点覆盖率、引用准确率、拒答正确率、答案长度。
- 性能：TTFT、总耗时、P95/P99、错误率、吞吐。
- 成本：token/次、GPU/CPU 占用、单位问答成本。

**压测**
```bash
# 现有应用基线（本地假模型）
python tools/loadtest/run_loadtest.py --levels 10,30 --yes

# 100 并发（确认空闲时段）
python tools/loadtest/run_loadtest.py --levels 50,100 --yes
```
- 先用假模型隔离上游，再换真实 LLM 验证端到端。
- 记录 P50/P95/P99、错误分类、资源峰值、日志中的排队/超时。
- 不要只看平均值；P95 才是用户体验。

## 7. Go / No-Go 标准

**Go**
- 解析质量满足主要文档类型；
- Recall@8 达到约定目标；
- 100 并发不雪崩，检索层 P95 达标；
- API 能满足 BFF 集成；
- 资源和许可证可接受。

**有条件 Go**
- 某类文档解析差：限定范围/人工预处理/换解析器。
- 100 并发需限流：先上 50 并发 + 排队。
- 需要 GPU：申请资源或降低重排频率。

**No-Go**
- 关键文档无法解析且无替代方案；
- 检索质量明显低于现有；
- 资源/许可证不可接受；
- API 无法满足权限/增量需求。

## 8. 失败时的备选方案

保留 BFF 适配层，把内核换成：
- Elasticsearch/OpenSearch（BM25 + kNN）+ TEI/Infinity embedding/rerank；
- 或 FastGPT（pgvector/Milvus）；
- 业务层不改，只换 Adapter。
