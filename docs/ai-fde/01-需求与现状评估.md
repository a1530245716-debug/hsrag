# 01 · 需求与现状评估（Discover）

> 本文件对应 FDE 流程的**发现 + 定义**阶段。目标不是讲技术，而是把“谁用、解决什么、什么算成功、有哪些硬约束”说清楚，并用压测数据给现状定性。

## 1. 项目一句话

面向项目交付/实施人员的**内网文档 RAG 问答系统**：把项目交接材料、部署手册、环境信息、操作文档、答辩 PPT 等变成可检索、可引用、可问答的知识库，后续可能推广到更多项目和部门。

## 2. 用户与场景

| 用户 | 典型任务 | 现在的痛点 |
|---|---|---|
| 新接手项目的实施/交付工程师 | “这个项目是什么、有哪些系统、环境信息在哪” | 翻几百份文档，找不到、看不懂、问老同事 |
| 现场实施人员 | “某系统怎么部署/升级/排查” | 手册分散，版本多，回答依赖个人经验 |
| 项目负责人 | “上线材料、配置表、验收清单有哪些” | 文档多、表格多，检索不到关键页 |
| 新人答辩/培训 | 模拟评委提问、参考答案、评分 | 缺少标准化练习和反馈 |
| 管理员 | 建库、分配权限、看问答日志 | 需要可控的权限、审计和运营数据 |

**核心场景**（按优先级）
1. 项目认知/交接：项目进展、系统关系、模块组成。
2. 部署升级：安装包、步骤、配置、回滚。
3. 环境信息：测试/UAT/生产的 IP、账号、数据库连接。
4. 运维排查：报错、日志、常见故障。
5. 文档定位：某份清单/配置表/验收材料在哪。
6. 模拟答辩：出题、回答、评分、解析。

## 3. 输入数据

- 类型：PDF、Word、PPT、Excel、图片/扫描件、手写笔记、网页导出。
- 特征：中文为主；表格多；扫描件/截图多；版本多（同族文档按时间降权）。
- 规模：当前最大库约 5.6 万块；单库 289 份文档；总量 GB 级。
- 更新：项目推进中持续新增/替换；需要增量索引，不能每次全量重建。
- 敏感性：客户项目资料、环境信息、账号密码、内部手册，**默认不能出内网**。

## 4. 硬约束

| 约束 | 说明 | 对方案的影响 |
|---|---|---|
| 内网/私有化 | 只有内网用户访问，服务器无公网 | 不能用 SaaS；模型/依赖要能离线部署 |
| 数据安全 | 客户资料、账号密码不能外传 | LLM 必须走内部网关；日志脱敏；权限后端强制 |
| 并发 | 目标 100 人在线，20~30 人同时提问 | 需要外部检索引擎、异步 API、限流/排队 |
| 权限 | 管理员/普通用户/分享只读；后续可能多项目隔离 | 权限在 BFF 强制，不能只靠平台 |
| 增量 | 持续新增/更新/删除文档 | 需要任务队列、版本、回滚 |
| 运维人力 | 目前基本一个人维护 | 组件要少而成熟；优先平台化，避免自研全套 |
| 预算 | 公司内网服务器，可能无 GPU | 优先 CPU 方案；预留 GPU 选项 |

## 5. 现状架构（改造前）

```
浏览器 → FastAPI（单进程，同步 SSE + 线程池）
           ├─ 认证/权限：users.json + 中间件
           ├─ BM25：Python 全量扫描 chunks.jsonl
           ├─ 向量：numpy 全量矩阵 + ONNX embedding
           ├─ 重排：ONNX reranker，信号量 2 路
           ├─ 生成：httpx 同步调用内部 LLM 网关
           ├─ 缓存/日志：进程内存 + 本地 JSONL
           └─ 索引：本地文件 + 后台线程
```

**已经做得好的地方**：功能完整、权限/分享/答辩/笔记/OCR/图片都有；BM25 旧索引先用、向量原子替换、缓存锁等细节考虑了并发安全；代码可读性不错。

**结构性问题**
1. 检索/重排/推理都在 Web 进程内，CPU 和 GIL 与请求处理互相拖累。
2. 同步 SSE 生成器占线程池（默认 40），普通接口会被拖慢。
3. 状态在进程内存/本地文件，无法水平扩展。
4. 没有外部检索引擎/向量库，5.6 万块的查询成本随并发线性上升。
5. 没有网关/队列/可观测性，缺少限流、降级和故障定位。

## 6. 压测基线（2026-11-11）

**测试方法**
- 知识库：56,426 块；18 条评测问题；关闭缓存（`no_cache`）。
- 假大模型：固定 2.3 秒/答、零错误，排除上游波动。
- 客户端并发发起 `/api/kb/{id}/ask/stream`，同时每秒探测 `/api/health` 和 `/api/kb`。
- 工具：`tools/loadtest/`（可复现）。

**结果**

| 并发 | 成功 | TTFT p50 | TTFT p95 | 总耗时 p95 | 墙钟 | 吞吐 | health p95 | health 超时 |
|---|---|---|---|---|---|---|---|---|
| 10 | 10/10 | 24.7s | 39.5s | 42.4s | 43s | 0.23/s | 995ms | 0 |
| 30 | 30/30 | 66.0s | 124.6s | 127.3s | 133s | 0.23/s | 1.3s | 0 |
| 50 | 50/50 | 127.4s | 170.5s | 173.3s | 185s | 0.27/s | 1.5s | 3 |
| 100 | 97/100 | 225.3s | 314.4s | 315.5s | 337s | 0.30/s | 2.0s | 18 |

**日志证据**
- 29 次重排排队超时（等待 120 秒后跳过重排）。
- 32 次大模型“流式生成超过 90 秒”，但假模型只需 2.3 秒——说明是应用侧线程/GIL 饥饿导致的假超时。
- 100 并发时 97% 请求 TTFT ≥ 120 秒，57% ≥ 200 秒。
- 100 个问题实际产生 125 次上游调用（改写/拆解带来约 1.25 次/问）。

**结论**
- 延迟随并发近似线性增长，瓶颈是串行化资源（重排 2 路、BM25 全扫、40 线程池），不是大模型。
- 换外部 API Key 只能解决上游并发，解决不了这组数据。
- 单进程架构在 100 并发下不可用；需要把检索引擎和推理从 Web 进程拆出去。

> 复现命令和参数说明见 `04-PoC实施与评测.md`。

## 7. 成功指标（建议 SLO）

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 并发在线 | 100 人 | 压测/监控 |
| 同时提问 | 20~30 | 压测 |
| 检索 P95 | < 500ms | 服务端埋点 |
| 重排 P95 | < 1s | 服务端埋点 |
| 首 token（不含上游排队） | < 2s | 客户端/网关 |
| 应用层 P95 | < 5s | 压测 |
| 错误率 | < 1% | 监控 |
| 超载行为 | 429 + 预计等待 | 限流测试 |
| 增量导入 | 10 份普通文档 < 5 分钟 | 任务计时 |
| 引用准确率 | 人工抽检 ≥ 90% | 评测集 |

## 9. 尚待确认的问题

3. 公司是否允许 Docker/容器？是否有内部镜像仓库？
4. 是否已有内部 AI 平台/模型网关可以直接接入？
5. 数据保留/审计/等保要求是什么？
6. 后续推广是一个部门，还是多项目/多租户？
