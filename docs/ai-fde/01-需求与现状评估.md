# 01 · 需求与现状评估（Discover）

> 本文件对应 FDE 流程的**发现 + 定义**阶段。目标不是讲技术，而是把“谁用、解决什么、什么算成功、有哪些硬约束”说清楚，并用压测数据给现状定性。

## 1. 项目一句话

面向项目交付/实施人员的**内网文档 RAG 问答系统**：把项目交接材料、部署手册、环境信息、操作文档、答辩 PPT 等变成可检索、可引用、可问答的知识库，后续可能推广到更多项目和部门。

## 2. 用户与场景

| 用户 | 典型任务 | 现在的痛点 |
|---|---|---|
| 新接手项目的实施/交付工程师 | “这个项目是什么、有哪些系统、环境信息在哪” | 翻几百份文档，找不到、看不懂、问老同事 |
| 现场实施人员 | “某系统怎么部署/升级/排查” | 手册分散，版本多，回答依赖个人经验 |
| 项目负责人 | “上线材料、配置表、验收清单有哪些” | 文档多、表格多，检索不到关键页 |
| 新人答辩/培训 | 模拟评委提问、参考答案、评分 | 缺少标准化练习和反馈 |
| 管理员 | 建库、分配权限、看问答日志 | 需要可控的权限、审计和运营数据 |

**核心场景**（按优先级）
1. 项目认知/交接：项目进展、系统关系、模块组成。
2. 部署升级：安装包、步骤、配置、回滚。
3. 环境信息：测试/UAT/生产的 IP、账号、数据库连接。
4. 运维排查：报错、日志、常见故障。
5. 文档定位：某份清单/配置表/验收材料在哪。
6. 模拟答辩：出题、回答、评分、解析。

## 3. 输入数据

- 类型：PDF、Word、PPT、Excel、图片/扫描件、手写笔记、网页导出。
- 特征：中文为主；表格多；扫描件/截图多；版本多（同族文档按时间降权）。
- 规模：当前最大库约 5.6 万块；单库 289 份文档；总量 GB 级。
- 更新：项目推进中持续新增/替换；需要增量索引，不能每次全量重建。
- 敏感性：客户项目资料、环境信息、账号密码、内部手册，**默认不能出内网**。

## 4. 硬约束

| 约束 | 说明 | 对方案的影响 |
|---|---|---|
| 内网/私有化 | 只有内网用户访问，服务器无公网 | 不能用 SaaS；模型/依赖要能离线部署 |
| 数据安全 | 客户资料、账号密码不能外传 | LLM 必须走内部网关；日志脱敏；权限后端强制 |
| 并发 | 目标 100 人在线，20~30 人同时提问 | 需要外部检索引擎、异步 API、限流/排队 |
| 权限 | 管理员/普通用户/分享只读；后续可能多项目隔离 | 权限在 BFF 强制，不能只靠平台 |
| 增量 | 持续新增/更新/删除文档 | 需要任务队列、版本、回滚 |
| 运维人力 | 目前基本一个人维护 | 组件要少而成熟；优先平台化，避免自研全套 |
| 预算 | 公司内网服务器，可能无 GPU | 优先 CPU 方案；预留 GPU 选项 |

## 5. 现状架构

### 5.1 改造前（2026-11-11 基线，保留作对照）

```
浏览器 → FastAPI（单进程，同步 SSE + 线程池）
           ├─ 认证/权限：users.json + 中间件
           ├─ BM25：Python 全量扫描 chunks.jsonl
           ├─ 向量：numpy 全量矩阵 + ONNX embedding
           ├─ 重排：ONNX reranker，信号量 2 路
           ├─ 生成：httpx 同步调用内部 LLM 网关
           ├─ 缓存/日志：进程内存 + 本地 JSONL
           └─ 索引：本地文件 + 后台线程
```

**已经做得好的地方**：功能完整、权限/分享/答辩/笔记/OCR/图片都有；BM25 旧索引先用、向量原子替换、缓存锁等细节考虑了并发安全；代码可读性不错。

### 5.2 当前架构（2026-11-13，第一轮优化已合并）

```
浏览器 → FastAPI（单进程，同步 SSE + 线程池 ← 阶段 2 待改）
           ├─ 认证/权限：users.json + 中间件（未变）
           ├─ BM25：内存 CSR 倒排索引，只扫命中词 ✅ 已改
           ├─ 向量：每查询 mmap + 写者优先读写锁 ✅ 已改
           ├─ 重排：ONNX reranker，并发 1 + 超时 10s ✅ 已改
           ├─ 生成：httpx 同步调用内部 LLM 网关（未变，阶段 2）
           ├─ 限流：三层（全局 20 / 每用户 2 / 每 IP 60次分）✅ 已加
           ├─ 缓存/日志：进程内存 + 本地 JSONL（未变）
           └─ 索引：本地文件 + 后台线程（未变）
```

### 5.3 结构性问题：已解决 / 未解决

| # | 问题 | 状态 | 证据 |
|---|---|---|---|
| 1 | 检索在 Web 进程内、GIL 拖累请求 | **已缓解** | 内存 CSR 倒排：5.6 万块查询 75–172ms → 1.6–7.0ms；建完释放 tf_list 约 330MB |
| 2 | 同步 SSE 生成器占线程池（默认 40） | **未解决** ← 阶段 2 | 放行请求首字仍 7–65 秒；`/api/health` 已单独改 async 缓解 |
| 3 | 状态在进程内存/本地文件，无法水平扩展 | **未解决** | 仍单进程单实例；多 worker 会内存 ×N |
| 4 | 没有外部检索引擎，查询成本随并发线性上升 | **部分缓解** | 倒排把单查询成本压到毫秒级，但仍在 Web 进程内，未外置 |
| 5 | 没有网关/队列/可观测性 | **部分缓解** | 已有限流 + 429；仍无队列、无 Prometheus 指标 |

**面试时的说法**：第一轮只做了「不动架构就能拿到收益」的部分（倒排、mmap、重排调参、限流），
一轮下来把单查询成本和过载行为都改善了；真正的架构性改造（异步化、外置检索、状态外置）
留给后续阶段，每阶段独立提交、可回滚。

## 6. 压测基线

### 6.1 改造前基线（2026-11-11）

**测试方法**
- 知识库：56,426 块；18 条评测问题；关闭缓存（`no_cache`）。
- 假大模型：固定 2.3 秒/答、零错误，排除上游波动。
- 客户端并发发起 `/api/kb/{id}/ask/stream`，同时每秒探测 `/api/health` 和 `/api/kb`。
- 工具：`tools/loadtest/`（可复现）。

**结果**

| 并发 | 成功 | TTFT p50 | TTFT p95 | 总耗时 p95 | 墙钟 | 吞吐 | health p95 | health 超时 |
|---|---|---|---|---|---|---|---|---|
| 10 | 10/10 | 24.7s | 39.5s | 42.4s | 43s | 0.23/s | 995ms | 0 |
| 30 | 30/30 | 66.0s | 124.6s | 127.3s | 133s | 0.23/s | 1.3s | 0 |
| 50 | 50/50 | 127.4s | 170.5s | 173.3s | 185s | 0.27/s | 1.5s | 3 |
| 100 | 97/100 | 225.3s | 314.4s | 315.5s | 337s | 0.30/s | 2.0s | 18 |

**日志证据**
- 29 次重排排队超时（等待 120 秒后跳过重排）。
- 32 次大模型“流式生成超过 90 秒”，但假模型只需 2.3 秒——说明是应用侧线程/GIL 饥饿导致的假超时。
- 100 并发时 97% 请求 TTFT ≥ 120 秒，57% ≥ 200 秒。
- 100 个问题实际产生 125 次上游调用（改写/拆解带来约 1.25 次/问）。

**结论**
- 延迟随并发近似线性增长，瓶颈是串行化资源（重排 2 路、BM25 全扫、40 线程池），不是大模型。
- 换外部 API Key 只能解决上游并发，解决不了这组数据。
- 单进程架构在 100 并发下不可用；需要把检索引擎和推理从 Web 进程拆出去。

> 复现命令和参数说明见 `04-PoC实施与评测.md`。

### 6.2 第一轮优化后（2026-11-13）

**测试条件**：与 6.1 完全一致（鑫元库 56,426 块、18 条问题、假模型 tokens=100 /
delay=0.02s / ttft=0.3s）。**这一条很重要**——参数不一致会让数字没法对比，
第一轮测的时候就踩过（错用了工具默认的 tokens=200，回答长度翻倍，看起来像退化）。

**限流生效后（每用户 2 路 / 全局 20）**

| 并发 | 放行 | 拒绝 | 放行请求首字 p50 | 基线 p50 |
|---|---|---|---|---|
| 10 | 2 | 8 | **8.0s** | 24.7s |
| 30 | 2 | 28 | **8.5s** | 66.0s |
| 50 | 2 | 48 | **8.5s** | 127.4s |

**只看全局层（临时把 per_user_max 放宽到 50）**

| 并发 | 放行/总数 | 首字 p50 | 基线 p50 |
|---|---|---|---|
| 10 | 10/10 | 35.9s | 24.7s |
| 30 | 20/30 | 61.3s | 66.0s |
| 50 | 20/50 | 64.9s | 127.4s |

**怎么读这两组数**（面试要点）：

- **被拒绝的请求从「等 127 秒」变成「立刻 429」**——这是阶段 1 的全部价值，
  用户不再干等，前端能提示「几秒后重试」。
- **放行的请求仍然慢**（35–65 秒）。因为限流只限制了并发数，没减少单请求的耗时；
  单请求慢是同步 SSE 占线程池造成的，要阶段 2（异步化）才治得了。
- 10 并发全局限流那组反而比基线慢（35.9s vs 24.7s），因为 Claude Code 的倒排和 mmap
  是在这批数据之后合并的，且两次运行的系统负载不同。**做对比必须同代码同参数重跑**，
  这条本身也是面试可以讲的踩坑。

**合并倒排索引 + mmap 后（阶段 1 代码，单点验证）**

5 并发并发提问：2 放行 / 3 个 429，放行请求首字 **7.0 秒**（合并前同一测试是 8.0 秒）。

> 完整的压测原始数据在 `tools/loadtest/results-*.json`，复现命令见 `04-PoC实施与评测.md`。

## 7. 成功指标（建议 SLO）与当前达成情况

| 指标 | 目标 | 当前（2026-11-13） | 差距 |
|---|---|---|---|
| 并发在线 | 100 人 | 未压测真实网关（会触发 429） | — |
| 同时提问 | 20~30 | 限流放行 20，超过立刻 429 | 已达「可预期」 |
| 检索 P95 | < 500ms | **1.6–7.0ms**（倒排后） | ✅ 超标达成 |
| 重排 P95 | < 1s | 约 3.9s/次（并发 1） | ❌ 未达标 |
| 首 token（不含上游排队） | < 2s | 8.0–8.5s（限流后放行请求） | ❌ 阶段 2 目标 |
| 应用层 P95 | < 5s | 放行请求 35–65s | ❌ 阶段 2 目标 |
| 错误率 | < 1% | 100 并发时 97/100 成功 | 近似达标 |
| 超载行为 | 429 + 预计等待 | ✅ 429 + `Retry-After: 5` | ✅ 已达成 |
| 增量导入 | 10 份普通文档 < 5 分钟 | 未测（索引仍是同步阻塞） | Claude Code 在做 |
| 引用准确率 | 人工抽检 ≥ 90% | 未系统抽检；评测 5/6 | 待补 |

**面试要点**：这张表是"目标 vs 现状"的诚实对比。已经超标的（检索）、已达成但要重建的
（超载行为）、明确没做完的（首 token、应用层 P95）都写清楚。比声称"全部达标"可信得多，
也正好引出下一步要做什么。
