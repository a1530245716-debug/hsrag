# 07 · 技术笔记：并发与 RAG 踩坑

> 这些是本次压测和代码审查得到的实战结论。换框架/平台后仍适用，因为问题本质是**资源模型**，不是某个库。

## 1. 基线数据先行

- 56,426 块，假模型 2.3 秒/答。
- 10 并发 p95 42 秒；100 并发 p95 315 秒。
- 100 并发：97% TTFT ≥ 120 秒，29 次重排排队超时，32 次 90 秒假超时。
- 结论：延迟随并发近似线性增长，瓶颈是串行化资源。

## 2. 同步 SSE 会占满线程池

- FastAPI 里 `def` 端点跑在 anyio 线程池，默认上限 **40**。
- 同步生成器（StreamingResponse）在等待上游 token 时，每次 `next()` 都占一个线程。
- 40 路流式问答后，登录、列表、健康检查一起排队。
- 现象：CPU 不高，但 `/api/health` 延迟 2 秒甚至超时。
- 解法：
  - `async def` + `httpx.AsyncClient.stream`，SSE 纯异步；
  - 检索/推理放独立 `CapacityLimiter` 或进程池；
  - 健康检查做成轻量异步端点。

> **2026-11-13 进度**：**健康检查已改 async**（`/api/health` 空闲 8–11ms，
> 基线 100 并发时 1985ms）；**SSE 主体仍是同步生成器**，尚未改。
> 这一步是阶段 2，也是当前收益最大的地方——放行请求首字仍是 7–65 秒。

## 3. GIL 是隐形杀手

- BM25 查询对 5.6 万块做纯 Python 循环，全程持 GIL。
- 40 个线程同时跑检索，事件循环和其他线程都拿不到 GIL。
- 表现：
  - 读 LLM 流的线程被饿死，`time.time() - t0 > 90` 触发假超时；
  - 日志出现“流式生成超过 90s”，但假模型只需 2.3 秒。
- 解法：
  - 倒排索引（只给命中词打分）或外部检索引擎；
  - 检索移到独立进程/进程池；
  - 避免在请求线程里做大循环。

> **2026-11-13 已落地**：内存 CSR 倒排（136,422 词 / 300 万 posting / 24MB），只给命中词打分。
> 5.6 万块查询 75–172ms → 1.6–7.0ms（20–49 倍），12 条查询 top-20 与旧实现**逐位相同**；
> 建完释放 `tf_list` 约 330MB。不落盘、不改 `chunks.jsonl`。

## 4. 重排信号量是硬瓶颈

- `RERANK_CONCURRENCY = 2`，排队最长 120 秒，超时静默降级。
- 每次对 20~45 个候选、每条最多 512 token 做 CPU 推理。
- 并发 10 时约 15 秒排队；并发 100 时约 150 秒，直接雪崩。
- 解法：
  - 候选降到 10~16；
  - ONNX `intra_op_num_threads=2`，避免每个会话抢满核；
  - 并发按核数配置；GPU 加速；
  - 高负载按规则跳过重排；
  - 独立重排服务 + 批量。

> **2026-11-13 实测修正**：16 vCPU 上 `intra_op_num_threads=2` + 4 路并发只有 0.19 job/s；
> 默认线程 + **并发 1** 是 0.30–0.32 job/s（并发 2 降到 0.28 且单请求耗时翻倍）。
> 单次推理已吃满核，「按核数配并发」不成立。最终只把 `RERANK_CONCURRENCY=2→1`，
> **超时保留 120s**：过载应由准入控制 429 决定，不能让排队的请求静默失去重排
> （那等于不可见地降质量）；候选 24→16 只是可选降级，不做默认。
> **线程/并发数必须在本机压，不能凭经验。**

## 5. 上游 LLM 的并发额度

- 公司网关每把 Key 约 2 路并发（代码注释实测）。
- 一次提问可能 1~3 次调用（改写、拆解、主回答、续写、配图核对）。
- 实测 100 问产生 125 次上游调用。
- 解法：
  - LLM 网关统一限流/排队/Key 池；
  - 减少不必要调用（无历史不改写、无需拆解不拆）；
  - 每用户 Key 作为兜底；
  - 429 时给出明确等待时间，不要无限重试。

> **2026-11-13 实测与进度**：本机直连网关压测发现**个人级 QPS 限流**——
> 30 并发时有 3/30 返回 `429 rate_limit_exceeded`（个人限流规则触发），
> p50 仍有 2.0s、全部成功。这条是**硬约束**，代码优化绕不过去，只能限流 + Key 池。
>
> 应用侧已加**三层限流**（全局 20 / 每用户 2 / 每 IP 60 次每分），
> 超限立刻返回 `429 + Retry-After: 5`，让过载在应用层就被挡住，
> 不会一路打到网关再被拒。网关侧的 Key 池/统一网关还没做（依赖服务器）。

## 6. 没有连接池

- `httpx.post` / `httpx.stream` 顶层调用每次新建连接。
- 并发高时握手/TLS/端口开销大，网关侧连接数暴涨。
- 解法：共享 `httpx.Client/AsyncClient`，配置 `limits` 和 keep-alive。

> **2026-11-13 状态：未做**。`app/llm.py` 仍是顶层 `httpx.post` / `httpx.stream`，
> 每次调用新建连接。这是阶段 2 的一部分（加 `chat_async` / `stream_async` 时
> 一并换成共享 `AsyncClient`）。同步版会保留，出问题能立刻切回。

## 7. 冷启动与缓存

- 启动预热只建 BM25；首个向量查询会 `np.load` 115MB、全量解析 5.6 万行。
- 多个线程同时首次查询会重复加载，内存翻倍、GIL 卡死。
- 解法：
  - 启动时预热 BM25 + 行缓存 + 向量（mmap）+ tokenizer + 模型；
  - 加锁保证只加载一次；
  - 未就绪返回 503/进度，不让请求触发同步构建；
  - 向量用 `mmap_mode="r"` 共享页缓存。

> **2026-11-13 实测补充**：mmap 加载 1.2ms vs 全量 28.8ms，matmul 速度不变；
> 8 线程同时首载从 104.6ms + 8×111MB 降到 8.5ms 且共享页缓存。
> **但 Windows 上被映射的文件无法 `os.replace`（实测 WinError 5）**，长期持有会让向量重建失败。
> 最终实现：每查询打开 → matmul → 关闭，meta 按 mtime 缓存，每 kb 写者优先读写锁 + 替换重试。

## 8. 状态在进程内存/文件

- BM25、行缓存、向量缓存、答案缓存、答辩 session 都在进程内。
- 多 worker 会内存 ×N、缓存/会话不一致；`registry.json`/`users.json` 写入无跨进程锁。
- 解法：
  - 检索进程池 + 只读索引；
  - Redis 放缓存/会话/限流；
  - Postgres 放用户/注册表/日志；
  - 不要直接 `--workers N`。

## 9. Nginx/网关的 SSE 坑

- 默认 `proxy_buffering on` 会把 token 攒到最后一次性返回。
- 需要：
  - `proxy_buffering off; proxy_cache off; gzip off;`
  - `proxy_read_timeout 300s;`
  - `proxy_http_version 1.1; proxy_set_header Connection "";`
  - 上传 `client_max_body_size 100m;`
- 浏览器代理 PAC 也要把内网域名设为直连。

## 10. Linux 迁移的具体坑

| 问题 | 现状 | 处理 |
|---|---|---|
| EMF/WMF 转图 | 用 PowerShell + System.Drawing | Linux 需 LibreOffice/ImageMagick，或接受缺失 |
| .doc 抽取 | antiword（可选） | Linux `apt install antiword` |
| 中文字体 | 依赖系统字体 | 安装 Noto CJK |
| 路径 | registry 存 Windows 绝对路径 | 迁移时重映射或重新索引 |
| 服务托管 | .bat/隐藏进程 | systemd |
| 文件锁 | 进程内锁 | 多进程用文件锁/数据库 |

## 11. 安全与配置

- `config.json` 明文存 API Key/管理员口令；仓库里还有旧隧道私钥。
- 生产用环境变量/密钥文件；权限 600；轮换默认口令。
- 不在日志里记录完整问题/答案中的敏感信息。
- 对外材料脱敏。

## 13. 一句话总结

**并发问题不是“换个框架”能解决的，而是把 CPU 密集、长连接、共享状态从 Web 进程里拿出去。** 谁拥有资源、谁排队、谁限流，想清楚这三件事，换不换 LangChain 都不重要。

## 14. 修复效果复盘（2026-11-13）

把上面的结论落到本项目后的实测结果，按「问题 → 证据 → 改动 → 结果」组织，面试可直接讲：

| 问题 | 改动 | 实测结果 |
|---|---|---|
| BM25 全量循环持 GIL | 内存 CSR 倒排，只扫命中词 | 75–172ms → 1.6–7.0ms（20–49x），top-k 逐位不变 |
| 多线程重复加载 115MB 向量 | 按查询 mmap + meta 缓存 + 写者优先锁 | 首载 104.6ms/8×111MB → 8.5ms/共享页；加载 28.8ms → 1.2ms |
| 重排并发 2 排队雪崩 | 并发 1，保留完整候选与重排（不静默降级） | 吞吐 0.28 → 0.30–0.32 job/s；单请求 7.2s → 3.9s |
| 过载时用户干等 127s | 三层限流 + 立即 429 | 50 并发首字 127.4s → 8.5s（RAG-Agent 压测） |
| 健康检查排在线程池后 | `/api/health` 改 async | 空闲 8–11ms（基线 100 并发 1985ms） |
| 建索引内存峰值未知 | 队列内 tracemalloc 采样 | 56,870 块全量重建峰值 192.5MB / 213s（Python 分配，下界） |
| 重建期间挤占请求线程 | 索引队列 + 持久化 `index_status.json` | 同库合并、失败重试 2 次；状态可查，不占 HTTP 线程 |

**评测现状**：5/6，与 11-05 基线一致。两个非回归项：

- xy-01 稳定 FAIL：答案写 `O-order`，用例只认 `oorder` 子串（`tokenize` 本就把两者归一）；
- xy-03 波动：有时不提 JDK，单独复跑两次均 PASS，属模型/改写不确定性。

**还没做的**：阶段 2 的 LLM/SSE 异步化。限流只解决「不排队」，放行请求的首字仍受同步流式占线程池影响，50 并发下仍需 35–65 秒——这是下一步收益最大的地方。

这也是一条面试可讲的取舍：**先用限流止血（1 天，行为可预期），再做异步化（2–3 天，改造成本高但根治）**；每阶段独立提交、可回滚，不做一次性大重写。
