# 07 · 技术笔记：并发与 RAG 踩坑

> 这些是本次压测和代码审查得到的实战结论。换框架/平台后仍适用，因为问题本质是**资源模型**，不是某个库。

## 1. 基线数据先行

- 56,426 块，假模型 2.3 秒/答。
- 10 并发 p95 42 秒；100 并发 p95 315 秒。
- 100 并发：97% TTFT ≥ 120 秒，29 次重排排队超时，32 次 90 秒假超时。
- 结论：延迟随并发近似线性增长，瓶颈是串行化资源。

## 2. 同步 SSE 会占满线程池

- FastAPI 里 `def` 端点跑在 anyio 线程池，默认上限 **40**。
- 同步生成器（StreamingResponse）在等待上游 token 时，每次 `next()` 都占一个线程。
- 40 路流式问答后，登录、列表、健康检查一起排队。
- 现象：CPU 不高，但 `/api/health` 延迟 2 秒甚至超时。
- 解法：
  - `async def` + `httpx.AsyncClient.stream`，SSE 纯异步；
  - 检索/推理放独立 `CapacityLimiter` 或进程池；
  - 健康检查做成轻量异步端点。

## 3. GIL 是隐形杀手

- BM25 查询对 5.6 万块做纯 Python 循环，全程持 GIL。
- 40 个线程同时跑检索，事件循环和其他线程都拿不到 GIL。
- 表现：
  - 读 LLM 流的线程被饿死，`time.time() - t0 > 90` 触发假超时；
  - 日志出现“流式生成超过 90s”，但假模型只需 2.3 秒。
- 解法：
  - 倒排索引（只给命中词打分）或外部检索引擎；
  - 检索移到独立进程/进程池；
  - 避免在请求线程里做大循环。

## 4. 重排信号量是硬瓶颈

- `RERANK_CONCURRENCY = 2`，排队最长 120 秒，超时静默降级。
- 每次对 20~45 个候选、每条最多 512 token 做 CPU 推理。
- 并发 10 时约 15 秒排队；并发 100 时约 150 秒，直接雪崩。
- 解法：
  - 候选降到 10~16；
  - ONNX `intra_op_num_threads=2`，避免每个会话抢满核；
  - 并发按核数配置；GPU 加速；
  - 高负载按规则跳过重排；
  - 独立重排服务 + 批量。

## 5. 上游 LLM 的并发额度

- 公司网关每把 Key 约 2 路并发（代码注释实测）。
- 一次提问可能 1~3 次调用（改写、拆解、主回答、续写、配图核对）。
- 实测 100 问产生 125 次上游调用。
- 解法：
  - LLM 网关统一限流/排队/Key 池；
  - 减少不必要调用（无历史不改写、无需拆解不拆）；
  - 每用户 Key 作为兜底；
  - 429 时给出明确等待时间，不要无限重试。

## 6. 没有连接池

- `httpx.post` / `httpx.stream` 顶层调用每次新建连接。
- 并发高时握手/TLS/端口开销大，网关侧连接数暴涨。
- 解法：共享 `httpx.Client/AsyncClient`，配置 `limits` 和 keep-alive。

## 7. 冷启动与缓存

- 启动预热只建 BM25；首个向量查询会 `np.load` 115MB、全量解析 5.6 万行。
- 多个线程同时首次查询会重复加载，内存翻倍、GIL 卡死。
- 解法：
  - 启动时预热 BM25 + 行缓存 + 向量（mmap）+ tokenizer + 模型；
  - 加锁保证只加载一次；
  - 未就绪返回 503/进度，不让请求触发同步构建；
  - 向量用 `mmap_mode="r"` 共享页缓存。

## 8. 状态在进程内存/文件

- BM25、行缓存、向量缓存、答案缓存、答辩 session 都在进程内。
- 多 worker 会内存 ×N、缓存/会话不一致；`registry.json`/`users.json` 写入无跨进程锁。
- 解法：
  - 检索进程池 + 只读索引；
  - Redis 放缓存/会话/限流；
  - Postgres 放用户/注册表/日志；
  - 不要直接 `--workers N`。

## 9. Nginx/网关的 SSE 坑

- 默认 `proxy_buffering on` 会把 token 攒到最后一次性返回。
- 需要：
  - `proxy_buffering off; proxy_cache off; gzip off;`
  - `proxy_read_timeout 300s;`
  - `proxy_http_version 1.1; proxy_set_header Connection "";`
  - 上传 `client_max_body_size 100m;`
- 浏览器代理 PAC 也要把内网域名设为直连。

## 10. Linux 迁移的具体坑

| 问题 | 现状 | 处理 |
|---|---|---|
| EMF/WMF 转图 | 用 PowerShell + System.Drawing | Linux 需 LibreOffice/ImageMagick，或接受缺失 |
| .doc 抽取 | antiword（可选） | Linux `apt install antiword` |
| 中文字体 | 依赖系统字体 | 安装 Noto CJK |
| 路径 | registry 存 Windows 绝对路径 | 迁移时重映射或重新索引 |
| 服务托管 | .bat/隐藏进程 | systemd |
| 文件锁 | 进程内锁 | 多进程用文件锁/数据库 |

## 11. 安全与配置

- `config.json` 明文存 API Key/管理员口令；仓库里还有旧隧道私钥。
- 生产用环境变量/密钥文件；权限 600；轮换默认口令。
- 不在日志里记录完整问题/答案中的敏感信息。
- 对外材料脱敏。

## 12. 上线前自检

```
[ ] SSE 是异步的，流式不占线程池
[ ] 检索不在 Web 进程里跑大循环
[ ] 重排有并发上限和降级
[ ] 上游有网关限流/Key 池
[ ] HTTP 客户端复用了连接池
[ ] 冷启动预热完成，未就绪有提示
[ ] 状态外置或明确单实例
[ ] Nginx SSE/超时/上传验证
[ ] 监控能看到每阶段延迟和队列
[ ] 密钥不在代码/仓库里
[ ] 备份和回滚演练
[ ] 100 并发压测通过或有明确 429 策略
```

## 13. 一句话总结

**并发问题不是“换个框架”能解决的，而是把 CPU 密集、长连接、共享状态从 Web 进程里拿出去。** 谁拥有资源、谁排队、谁限流，想清楚这三件事，换不换 LangChain 都不重要。
