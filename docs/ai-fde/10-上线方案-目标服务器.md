# 10 · 目标服务器评估与上线方案

> 目标服务器：`10.20.154.26`（hostname `zg-test-r2`，VMware 虚拟机）
> 评估日期：2026-11-16。**只读评估，未安装、未改配置、未重启任何服务。**
> 登录凭据由人保管，本文不记录密码；上线前请轮换。

## 0. 结论先行

**可以上第一阶段（当前单进程 FastAPI + 本地 BM25/ONNX），但有三个硬约束：**

1. **RHEL 7.5（2018 年内核，已 EOL）**：glibc 2.17、OpenSSL 1.0.2，系统仓库无 python3；
2. **没有外网**：PyPI 不通，必须离线安装；内网 Artifactory 需要认证；
3. **内存只剩约 11GB 可用**：现有 `hsserver/hsmpas/learn-center` 已占约 52GB。

**不建议把 RAGFlow / 多 worker / Redis+Postgres 放在这台机器上**：没有 Docker、
11GB 可用内存、50GB 可用磁盘、RHEL7 过旧。RAGFlow 阶段建议换新 VM 或先升级 OS。

如果要直接做正式生产，推荐 **方案 B（新 VM / RHEL8-9 / Ubuntu 22.04）**；
这台更适合做测试/预发或第一阶段上线。

## 2. 关键技术卡点：Python / ONNX Runtime

RHEL7 的 glibc 是 **2.17**，只接受 `manylinux2014` wheel。实测（用 pip 的
`--platform manylinux2014_x86_64` 下载验证）：

| 组件 | 最新版 | RHEL7 可用版本 |
|---|---|---|
| Python | 3.12/3.14 | 无 yum 包；需自带运行时 |
| onnxruntime | 1.31 | **只有 1.16.3 有 cp311 manylinux2014 wheel**；1.17+ 要求更高 glibc |
| numpy | 2.5 | 1.26.4 / 2.2.6（manylinux2014） |
| pydantic-core | 2.41.5 | 有 cp311 manylinux2014 |
| tokenizers | 0.23.3 | cp310-abi3 manylinux2014，可用 |
| pymupdf | 1.28 | 1.26.0 |
| pillow | 12.3 | 12.2.0 |
| lxml / opencv | 最新 | 5.4.0 / 4.10.0.84（manylinux2014） |

因此第一阶段的固定组合是：

```
Python 3.11.18 (python-build-standalone, x86_64-unknown-linux-gnu, glibc 2.17)
onnxruntime==1.16.3
numpy==1.26.4
tokenizers==0.23.3
pydantic==2.14.1 / pydantic-core==2.41.5
pymupdf==1.26.0
pillow==12.2.0
lxml==5.4.0
opencv-python-headless==4.10.0.84   # rapidocr 用；不用 OCR 可省略
```

**代码兼容补丁**：`app/indexer.py:439` 用了 `Path.walk()`（Python 3.12+），
Python 3.11 需改成 `os.walk(root)`（`indexer.py` 已 import os），语义一致。
上线前用 Python 3.11 `compileall` 全量检查，确认没有其他 3.12+ 语法。

> 如果坚持 Python 3.12 + 最新 onnxruntime，**必须换 glibc ≥2.28 的系统**
> （RHEL8/9、Ubuntu 20.04+），这不是装个包能解决的。

## 3. 方案 A：第一阶段上线（当前应用，测试/预发）

### 3.1 拓扑

```
内网浏览器
   │  (仅内网/白名单)
Nginx 8080 (HTTP) / 8443 (HTTPS, 可选)
   │  proxy_buffering off; read_timeout 300s; client_max_body_size 100m
uvicorn 127.0.0.1:8000  (user: rag)
   ├─ app/data (chunks/vectors/image_index/上传/用户/注册表)
   ├─ models   (bge-small-zh-onnx + bge-reranker-base-int8-onnx，374MB)
   └─ LLM 网关 http://lightcode-uis.hundsun.com:8080（已可达）
```

- **不使用 8123**；80 已被 learn-center 占用；22/25/100xx 保持不动。
- 8000 只监听 127.0.0.1，外部统一走 Nginx；如果没有 Nginx，可直接监听
  10.20.154.26:8000，但必须加网络 ACL。

### 3.2 目录与用户

```
/opt/rag/
  python/           # Python 3.11.18 standalone
  wheels/           # 离线 wheel 包
  app/              # 代码
  models/           # 374MB
  data/             # app/data，1.1GB
  index/            # 66MB
  docs/             # 客户源文档（用于预览/图片；需重映射 registry.folder）
  logs/
/etc/rag/rag.env    # API Key 等，权限 600，不进 git
```

创建专用用户 `rag`，不要用 root 跑服务；数据目录属主 `rag:rag`。

### 3.3 离线安装包（在能上网的机器上准备）

服务器无 PyPI；用本机（有代理）准备：

```bash
# 1) Python 3.11.18 便携包
# https://github.com/astral-sh/python-build-standalone/releases/download/20261110/
#   cpython-3.11.18+20261110-x86_64-unknown-linux-gnu-install_only.tar.gz

# 2) 目标平台 wheel（在 Windows/有网机器上）
pip download -r requirements-server.txt \
  --only-binary=:all: --platform manylinux2014_x86_64 \
  --python-version 311 --implementation cp --abi cp311 \
  -d wheels/ --proxy http://127.0.0.1:7890

# requirements-server.txt 固定版本见第 2 节；另加：
# fastapi uvicorn httpx jieba python-docx python-pptx openpyxl xlrd
# python-multipart olefile（OCR 需要时再加 rapidocr-onnxruntime + opencv-python）
```

上传 `python.tar.gz + wheels/ + app/ + models/ + data/ + index/` 到服务器；
用 `tar`/SFTP 均可（服务器没有 rsync，可 yum 装）。

### 3.4 数据迁移与路径重映射

- 复制 `app/data`（1.1GB）、`models`（374MB）、`index`（66MB）；
- **registry.json 里的 `folder` 是 Windows 绝对路径**，Linux 上文件预览/图片会失败。
  需要把每个库的源目录复制到 `/opt/rag/docs/<kb_id>`，并把 `folder` 改为该路径；
  纯上传库保留 `upload` 目录即可；
- 校验 `chunks.jsonl` 行数、`vectors.npy` 行数、`index` 完整性；
- 注意 Linux 下 EMF/WMF、字体、antiword 的差异（07 第 10 节）；OCR 不是核心检索的
  必需项，缺依赖时先关闭扫描件 OCR，不影响已有 chunks 的问答。

### 3.5 配置与启动

1. `app/config.example.json` → `app/config.json`：
   - `server.host = 127.0.0.1`、`port = 8000`；
   - `figures.enabled = false`（当前决定不展示图片，图片知识保留在 chunks）；
   - `ask_limits = {global_max:6, per_user_max:2, per_ip_per_min:60, retry_after:5}`；
   - `retrieval` 保持；`backend.default = local_bm25`；
   - LLM 的 key 只放 `/etc/rag/rag.env`，不要写进 git，config 权限 600。
2. systemd（RHEL7 systemd 219 可用）：

```ini
[Unit]
Description=RAG BFF
After=network-online.target

[Service]
User=rag
WorkingDirectory=/opt/rag/app
EnvironmentFile=/etc/rag/rag.env
ExecStart=/opt/rag/python/bin/python3.11 app/server.py --port 8000
Restart=always
RestartSec=3
LimitNOFILE=65536
MemoryLimit=4G
NoNewPrivileges=true

[Install]
WantedBy=multi-user.target
```

3. Nginx（可选，EPEL 内网镜像可装）：
   `proxy_buffering off; proxy_cache off; gzip off; proxy_read_timeout 300s;`
   `proxy_http_version 1.1; proxy_set_header Connection "";`
   `client_max_body_size 100m;` 只放行内网网段。
4. 防火墙/SELinux 当前关闭：至少用网络 ACL/安全组只允许内网客户端；不要直接暴露公网。
   如需对外，走公司 Nginx/Tailscale/Cloudflared，或申请 TLS 证书。

### 3.6 验收

- `/api/health` 200；`/api/warmup` 预热完成；
- `eval/run_eval.py` **6/6**；
- 登录、权限、引用、文件预览/图片（按路径迁移情况）；
- 重启/断电重启后 systemd 自启；
- 4/6 并发小压测（不要直接上 20/100），与 Windows 基线对比；
- 备份 `app/data` + config + 模型，做一次恢复演练。

### 3.7 回滚

保留 Windows 8000 生产实例作为回退；新服务器验收不通过就停 systemd、
客户端指回原服务。数据是拷贝，不存在双写。

## 3.8 Docker 容器化选项：为什么第一阶段不用

项目文档里的 Docker 方案分两种，先区分清楚：

| 场景 | 文档 | 要求 |
|---|---|---|
| 本机 demo / RAGFlow PoC | `tools/local_dev/docker-compose.yml`、`poc/install-docker-wsl.md` | Docker Engine + Compose v2（WSL2 或 Linux） |
| 目标生产架构 | `03`/`04`/`05` | **Docker 24+ / Compose v2**，RAGFlow 容器栈 |

这台服务器的实际情况：

- yum 只有 **docker 1.13.1**（CentOS7 extras，2017 年）和 **podman 1.6.4**；
  没有 docker-ce、没有 Compose v2；
- kernel 3.10，`overlay` 未在支持列表，Docker 只能用 devicemapper，性能和稳定性都差；
- 内网有 `registry.hundsun.com`（302，需认证），`harbor/nexus` 域名未解析；
  没有外网，镜像只能从内网仓库拉或离线 `docker save/load`。

**结论：第一阶段不要用 Docker。**

- Docker 1.13 不支持现代 OCI 镜像/Compose v2，RAGFlow 官方镜像跑不起来；
- 即使把当前应用打成镜像，也要先换 Docker CE 20.10（RHEL7 最后支持版本）+
  Compose v2 二进制，还要在别的机器构建、`docker save/load`，比 venv/systemd
  多一层复杂度，对单机没有收益；
- 第一阶段用 **Python 3.11 venv + systemd**（3.4/3.5）更稳。

**如果一定要容器化当前应用**，最低前提：

1. 从内网仓库/离线包装 **Docker CE 20.10** + Compose v2（不要用 1.13）；
2. 在能上网/有 Docker 的机器上构建镜像：
   `python:3.11-slim`（Debian，glibc 2.31）+ 固定 wheels（ORT 1.16.3），
   `docker save` 后上传 `docker load`；
3. 数据/模型用 volume 挂载；Nginx 可放宿主机或容器；
4. 用 `docker compose` + systemd 托管；端口仍用 8000/8080/8443，不用 8123；
5. 资源：当前应用约 1–2GB，容器开销小；但仍受 62GB/11GB 可用内存限制。

**RAGFlow/阶段 2**：必须走方案 B（新 VM + Docker 24+/Compose v2 + 32GB 以上可用内存
+ 500GB 磁盘）；这台 RHEL7 不适合。内网 `registry.hundsun.com` 可作为镜像来源，
但需要确认认证/项目权限。

## 5. 风险与需要确认的事

| 风险 | 影响 | 建议 |
|---|---|---|
| RHEL 7.5 EOL | 无安全更新；glibc 2.17 只能跑旧 ORT | 测试可接受；生产换 OS/新 VM |
| 只有 11GB 可用内存 | 当前应用约 1–2GB 可跑；RAGFlow 不够 | systemd `MemoryLimit=4G`；监控；不要共置 RAGFlow |
| 50GB 可用磁盘 | 当前数据+模型约 1.5GB；日志/备份/RAGFlow 会紧张 | 监控；RAGFlow 需扩容 |
| 无外网 / Artifactory 401 | 不能直接 pip 安装 | 离线 wheel；或申请 Artifactory PyPI/conda 只读账号 |
| 无 python3 / 无 nginx / 无 git | 初始化成本 | 便携 Python 3.11；EPEL 装 nginx；yum 装 git/rsync |
| firewall/SELinux 关闭 + root 密码 | 安全面大 | 建 `rag` 用户、SSH key、禁用 root 密码、网络 ACL、TLS |
| 现有 hsserver/hsmpas/learn-center | 不能动它们的端口/服务 | 只用 8000/8080/8443；变更前通知 |
| Windows 路径/EMF/字体 | 预览/图片/OCR 退化 | 数据路径重映射；补字体/antiword；OCR 可后置 |
| ORT 1.16.3 降级 | 推理性能/opset 兼容需验证 | 上线前同一模型跑 eval + 4/6 压测 |
| Docker 1.13 / 无 Compose v2 | 现代镜像与 RAGFlow 跑不了 | 第一阶段不用 Docker；阶段 2 新 VM + Docker 24+ |
| 8123 不可用 | 端口规划 | 使用 8000 + 8080/8443；不使用 8123 |

## 6. 建议的执行顺序

1. **确认走 A 还是 B**（测试/预发 vs 正式生产）；
2. 申请维护窗口与网络 ACL；确认现有服务不受影响；
3. 准备离线包：Python 3.11.18 + 固定 wheels + 代码补丁（`Path.walk`）；
4. 复制代码/模型/数据，重映射 registry 路径；
5. 启动 8000，health + eval 6/6 + 4/6 小压测；
6. 加 Nginx/HTTPS/ACL，systemd 自启，重启验证；
7. 备份/监控/回滚演练；通过后再切流。

**工作量预估**：离线包 0.5–1 天；部署+数据 2–4 小时；验收 1–2 小时；
建议预留半天窗口。若选方案 B（新 VM/OS），另加 1–2 天环境准备。
