## 一、问题定义（有实测证据，不是推测）

### 1.1 压测基线

| 并发 | 首字 P50 | 首字 P95 | QPS | `/api/health` P95 |
|---|---|---|---|---|
| 10 | 24.7s | 39.5s | 0.23 | 995ms |
| 30 | 66.0s | 124.6s | 0.23 | 1326ms |
| 50 | 127.4s | 170.5s | 0.27 | 1537ms |
| 100 | 225.3s | 314.4s | 0.30 | 1985ms |

**关键观察**：连 `/api/health` 都涨到 2 秒 —— 这不是"问答慢"，是**线程池被占满，所有请求一起排队**。

采集环境：8010 端口测试实例、本地假模型（`tools/loadtest/mock_llm.py`）、鑫元库 56426 块、16 vCPU。
**这些数字只反映服务端资源模型，不代表真实网关延迟。**

### 1.2 真实网关实测（2026-11-12，本机直连）

| 并发 | 墙钟 | p50 | 结果 |
|---|---|---|---|
| 1 | 2.96s | — | 正常 |
| 4 | 22.25s | 4.4s | 有一次卡到 22s |
| 8 | 7.19s | 2.0s | 全部成功 |
| **30** | 3.80s | 2.0s | **3 条 429**（`个人限流规则触发`） |

**结论**：网关有个人级 QPS 限流，30 并发就触发。这不是代码能优化的，只能靠限流 + Key 池绕开。

### 1.3 五个根因（代码行级）

| # | 根因 | 位置 | 说明 |
|---|---|---|---|
| 1 | 同步 SSE 占线程池 | `server.py:2099` `def gen()`；`llm.py:318/361` `httpx.stream` | uvicorn 默认 40 线程，每个占 10-90 秒 |
| 2 | BM25 纯 Python 循环持 GIL | `kb.py` 对 5.6 万块循环 | 健康检查也变慢的原因 |
| 3 | 重排信号量只有 2 路 | `RERANK_CONCURRENCY = 2` | 100 并发排队约 150 秒 |
| 4 | 没有连接池 | `llm.py` 顶层 `httpx.post` / `httpx.stream` | 每次新建 TCP/TLS |
| 5 | 网关个人限流 | 每把 Key 约 2 路并发 | 30 并发触发 429 |

对应 `docs/ai-fde/07-技术笔记-并发与RAG踩坑.md` 的 1-6 节，已核对代码属实。

## 二、阶段划分

```
阶段 1（止血）    1 天    → 50 并发 P95: 173s → <10s（直接 429）
阶段 2（异步化）  2-3 天  → 50 并发首字 P50: 127s → <10s
阶段 3（解耦）    3-5 天  → 检索可换内核，为 RAGFlow 铺路
阶段 4（状态外置）视情况  → 支持多 worker（当前不做）
```

**原则**（来自 `docs/ai-fde/README.md` 第 17 行）：
- 不为了并发重写成 LangChain
- 不一次性大爆炸重写
- 用 BFF 适配层保证随时可回退

## 三、阶段 1：止血（1 天）

**目标**：过载时明确拒绝，不让用户干等 5 分钟。

### 3.1 三层限流

依据 `docs/ai-fde/03-目标架构与数据权限.md:129`：

```
限流：全局活跃问答数、每用户并发数、每 IP 频率
超载返回 429 + Retry-After，不要让用户等几分钟
```

实施位置：`app/server.py`

```python
# 全局活跃问答数（网关实测 30 并发触发 429，留余量设 20）
GLOBAL_MAX_ASK = 20
_global_sem = asyncio.Semaphore(GLOBAL_MAX_ASK)

# 每用户并发
PER_USER_MAX_ASK = 2
_user_sems: dict[str, asyncio.Semaphore] = {}

# 每 IP 频率（令牌桶，60 次/分钟）
```

超限返回：
```json
{"ok": false, "msg": "系统繁忙，请稍后重试"}
```
`HTTP 429` + `Retry-After: 5`

### 3.2 健康检查轻量化

依据 `07:21`：「健康检查做成轻量异步端点」

`/api/health` 从 `def` 改 `async def`，从线程池里挪出来。

### 3.3 减少不必要调用

依据 `07:54`：「减少不必要调用（无历史不改写、无需拆解不拆）」

| 调用 | 位置 | 现状 |
|---|---|---|
| `rewrite_query` | `server.py:2154` | 检查是否已在无历史时跳过 |
| `plan_queries` | `server.py:2160` | `planner.py:110` 已用 `need_split()` 前置，无需改 |

### 3.4 验收

- 50 并发压测，P95 从 173 秒降到 **< 10 秒**（直接 429，不排队）
- `eval/run_eval.py` 6 条不退化
- 正常单人使用体验不变

## 四、阶段 2：异步化（2-3 天）

**目标**：线程不再被长时间占用。

### 4.1 `llm.py` 加异步接口

依据 `07:62`：「共享 `httpx.Client/AsyncClient`，配置 `limits` 和 keep-alive」

保留同步版（兼容现有调用），新增：

```python
_async_client: httpx.AsyncClient | None = None

def _get_async_client() -> httpx.AsyncClient:
    global _async_client
    if _async_client is None:
        _async_client = httpx.AsyncClient(
            timeout=httpx.Timeout(connect=10, read=60, write=10, pool=10),
            limits=httpx.Limits(max_connections=200, max_keepalive_connections=100),
        )
    return _async_client

async def chat_async(messages, cfg=None, system=None, timeout=None,
                     meta=None, user_key="") -> str: ...

async def stream_async(messages, cfg=None, system=None, meta=None,
                       user_key="", retries=3) -> AsyncIterator[str]: ...
```

### 4.2 SSE 端点改异步

依据 `07:19`：「`async def` + `httpx.AsyncClient.stream`，SSE 纯异步」

```python
# 现在（server.py:2070 / 2099）
def kb_ask_stream(kb_id, body, request):
    def gen(): ...
    return StreamingResponse(gen(), ...)

# 改成
async def kb_ask_stream(kb_id, body, request):
    async def gen(): ...
    return StreamingResponse(gen(), ...)
```

### 4.3 CPU 密集部分挪出事件循环

依据 `07:30-33`：「检索移到独立进程/进程池」

```python
from fastapi.concurrency import run_in_threadpool
results = await run_in_threadpool(
    kb.hybrid_search, kb_id, q_eff,
    topk=topk_, enable_vector=..., enable_rerank=...)
```

**注意**：这仍然占线程，但只占 0.1-2 秒，不占 90 秒。

### 4.4 客户端断开时取消上游

依据 `03:128`：「客户端断开时取消上游请求，避免继续消耗额度」

```python
async for token in llm.stream_async(...):
    if await request.is_disconnected():
        break
    yield sse("delta", {"text": token})
```

### 4.5 验收

- 50 并发压测，首字 P50 从 127 秒降到 **< 10 秒**
- `/api/health` P95 回到 **< 100ms**
- `eval/run_eval.py` 6 条不退化

## 六、阶段 4：状态外置（当前不做）

依据 `07:74-82`：

| 状态 | 现在 | 目标 |
|---|---|---|
| BM25 索引 | 进程内存 | 独立进程 / ES |
| 行缓存/向量缓存 | 进程内存 | mmap 共享 |
| 答案缓存 | 进程内存 | Redis |
| 答辩 session | 进程内存 | Redis |
| `registry.json` / `users.json` | 本地文件无锁 | Postgres 或文件锁 |

**关键约束**（`07:82`）：**不要直接 `--workers N`**。多 worker 会内存 ×N、缓存和会话不一致、文件写入无跨进程锁。必须先外置才加 worker。

**为什么现在不做**：需要 Redis/Postgres，属于服务器阶段。`docs/ai-fde/03` 的迁移路线里这是"全量"阶段的事。
