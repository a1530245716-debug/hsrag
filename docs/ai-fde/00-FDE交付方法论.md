# FDE 交付方法论：从需求到推广的完整流程

> FDE（Forward Deployed Engineer）不是“驻场开发”，而是**带着工程能力贴近客户，把不成熟的 AI 能力变成可上线、可运维、可复制的解决方案**。
>
> 本文是一套可复用的九阶段流程。每个阶段都给出：目标、关键问题、交付物、质量门、常见坑、在本项目中的落点。

## 0. 总览

| 阶段 | 一句话目标 | 核心交付物 | 质量门 |
|---|---|---|---|
| 1 发现 Discover | 搞清楚谁用、用来干什么、什么算成功 | 需求一页纸、用户画像、约束清单 | 业务方确认目标与范围 |
| 2 定义 Define | 把目标变成可验收的 SLO 和边界 | SLO、验收标准、风险清单、里程碑 | 双方签字/邮件确认 |
| 3 设计 Design | 选型 + 架构 + 数据/权限/部署方案 | 架构图、ADR、数据模型、容量估算 | 架构评审通过 |
| 4 原型 Prototype | 用真实数据跑通一条端到端链路 | PoC 版本、演示脚本 | 关键场景可演示 |
| 5 验证 Validate | 用评测、压测、安全评审证明可行 | 评测报告、压测报告、安全清单 | 指标达标，或明确降级方案 |
| 6 上线 Deploy | 私有化部署、接入权限和监控 | 部署包、运行手册、回滚方案 | 上线检查表全绿 |
| 7 运维 Operate | 稳住 SLO，快速定位和恢复 | 监控面板、告警、故障手册 | 7 天观察期无 P0/P1 |
| 8 推广 Adopt | 让用户真正用起来并形成反馈闭环 | 培训材料、试点计划、使用指标 | 活跃用户/问答量达标 |
| 9 演进 Evolve | 增量扩展、回归评测、版本升级 | 迭代计划、回归报告、路线图 | 每次变更都有评测对比 |

## 1. 发现 Discover

**目标**：理解业务，而不是先想技术。

**关键问题**
- 谁用？每天/每周用多少次？现在怎么做？痛在哪？
- 输入是什么：文档类型、扫描件、表格、图片、大小、更新频率？
- 输出要多准？错了会怎样？谁负责最终判断？
- 有哪些硬约束：内网、数据不出域、等保/审计、账号体系、并发、预算？
- 成功怎么衡量：节省时间、减少求助、首次解决率、满意度？

**交付物**
- 需求一页纸：用户、场景、输入、输出、约束、成功指标。
- 用户画像与典型任务清单。
- 数据样本清单（脱敏）和更新机制。

**质量门**：业务方确认“要解决什么问题、不解决什么”。

**常见坑**：把“做个 AI 问答”当需求；忽略权限和审计；低估文档脏乱程度。

**本项目落点**：见 `01-需求与现状评估.md`。

## 2. 定义 Define

**目标**：把模糊需求变成可验收的工程目标。

**关键问题**
- 并发是多少人在线、多少人同时提问？峰值在什么时候？
- 延迟目标：首 token、完整回答、检索、重排分别是多少？
- 准确率：召回率、引用准确率、拒答正确率的目标？
- 可用性：能否接受降级？故障时用户看到什么？
- 数据边界：哪些文档绝不能出内网？保留多久？谁审计？

**交付物**
- SLO 表（分阶段、可测量）。
- 验收标准与测试方法。
- 风险清单和假设清单。
- 里程碑与“不做什么”。

**质量门**：SLO 可被压测/评测直接验证；双方对边界无歧义。

**常见坑**：只写“要快、要准”；没有定义“准”的评测集；没有降级策略。

**本项目建议 SLO**
- 100 人在线，20~30 人同时提问；
- 检索 P95 < 500ms，重排 P95 < 1s，首 token（不含上游排队）< 2s；
- 应用层 P95 < 5s，整体受 LLM 影响另计；
- 错误率 < 1%，排队超时返回 429 并给出预计等待；
- 增量导入 10 份普通文档 < 5 分钟。

## 3. 设计 Design

**目标**：做出能落地、能扩展、能回退的设计。

**关键问题**
- 哪些是商品化能力（解析、检索、向量、重排、模型调用），哪些是差异化能力（权限、业务规则、UI、行业知识）？
- 状态放哪？能否水平扩展？故障域在哪？
- 权限在哪里强制？平台还是 BFF？
- 增量、删除、版本回滚怎么处理？
- 怎么观测：每阶段耗时、队列、错误、成本？

**交付物**
- 架构图与组件职责。
- ADR（架构决策记录）：每个关键选择写“背景/选项/决定/后果”。
- 数据模型与权限矩阵。
- 容量与部署拓扑。
- 迁移与回滚方案。

**质量门**：架构评审通过；每个单点故障有应对；能说清“为什么不选另一个”。

**常见坑**：把平台当万能；权限交给平台却对不上业务；没有回退路径；过度微服务化。

**本项目落点**：`02-技术选型与方案.md`、`03-目标架构与数据权限.md`。

## 4. 原型 Prototype

**目标**：用真实数据跑通一条最小闭环，尽早暴露问题。

**做法**
- 选一个知识库、20~50 个真实问题、一条完整链路（上传→解析→检索→重排→生成→引用）。
- 先不做权限/多租户/复杂 UI，但要在真实网络和真实文档上跑。
- 记录每个阶段的耗时和失败原因。

**交付物**
- 可演示的 PoC。
- PoC 日志和问题清单。
- 与现有系统的对比（质量、延迟、成本）。

**质量门**：关键场景可演示；解析质量和检索质量达到可接受下限。

**常见坑**：只用干净 PDF 演示；忽略扫描件/表格；不做并发；把演示当生产。

**本项目落点**：`04-PoC实施与评测.md`。

## 5. 验证 Validate

**目标**：用数据证明“能上线”，而不是“看起来能用”。

**三类验证**
- **质量**：评测集（召回、正确性、引用、拒答）。
- **性能**：并发、P95/P99、错误率、资源占用。
- **安全与合规**：权限、审计、密钥、数据边界、依赖漏洞。

**交付物**
- 评测报告（含基线、改动、结论）。
- 压测报告（场景、指标、瓶颈、建议）。
- 安全评审清单。
- Go/No-Go 结论。

**质量门**：SLO 达标；不达标时有明确的降级/扩容方案；评测可复现。

**常见坑**：只测平均不测 P95；用假数据；不记录版本；评测集泄漏到提示词。

**本项目落点**：`04-PoC实施与评测.md` + `tools/loadtest/`。

## 6. 上线 Deploy

**目标**：稳定、可回滚地交付到客户环境。

**上线检查表**
- 服务器规格、磁盘、内存、CPU 预留；
- 内网 IP/DNS/证书/防火墙；
- 服务账号、文件权限、密钥管理；
- 数据库/对象存储/缓存/检索引擎的持久化与备份；
- Nginx/网关：SSE 不缓冲、超时、上传大小、TLS；
- 进程守护、开机自启、健康检查；
- 日志轮转、监控告警；
- 回滚包与回滚演练；
- 用户通知与培训。

**交付物**：部署包、运行手册、回滚手册、上线检查表。

**质量门**：检查表全绿；回滚演练成功；监控能看到核心指标。

**常见坑**：直接暴露应用端口；没关 SSE 缓冲；把密钥写进配置文件；没做备份。

**本项目落点**：`05-生产部署与运维.md`。

## 7. 运维 Operate

**目标**：守住 SLO，出问题能快速定位。

**必备观测**
- 每阶段延迟：检索、重排、LLM 首 token、生成总时长；
- 队列深度、活跃请求、线程/连接池占用；
- 错误分类：检索空、重排超时、LLM 429/5xx/超时、权限拒绝；
- 资源：CPU、内存、磁盘、连接数；
- 业务：问答量、活跃用户、缓存命中、反馈率。

**故障手册**：症状 → 可能原因 → 检查命令 → 处置 → 回滚。

**质量门**：7 天观察期无 P0/P1；每个告警有对应处置。

**常见坑**：只有 CPU/内存监控；日志没有 trace id；故障时只能重启。

**本项目落点**：`05-生产部署与运维.md` 的故障手册部分。

## 8. 推广 Adopt

**目标**：让用户从“能访问”变成“愿意用、持续用”。

**做法**
- 选 5~10 个种子用户，做 2 周试点；
- 提供 3 个高频场景的演示脚本；
- 培训 + 一页纸速查 + 视频；
- 建立反馈渠道（点赞/点踩 + 每周复盘）；
- 用数据说话：问答量、活跃用户、首次解决率、节省时间。

**交付物**：试点计划、培训材料、反馈闭环、使用报告。

**质量门**：试点用户周活跃达标；高频问题 Top 20 有答案；负面反馈有闭环。

**常见坑**：上线即结束；没有种子用户；不做培训；不看使用数据。

**本项目落点**：`06-上线推广与交接.md`。

## 9. 演进 Evolve

**目标**：增量扩展而不破坏已有质量。

**做法**
- 每次改检索/模型/提示词，必须跑回归评测；
- 新知识库先灰度，再全量；
- 版本化配置和索引，保留回滚；
- 每季度复盘：质量、性能、成本、用户反馈。

**交付物**：迭代路线图、回归报告、版本记录。

**质量门**：回归指标不低于基线；回滚可用。

**本项目落点**：`04` 的评测流程 + `05` 的升级回滚。

## 一页纸检查表（可直接复制到交付文档）

```
[ ] 需求一页纸已确认
[ ] 用户/场景/输入/输出/约束清晰
[ ] SLO 可测量，验收方法已定义
[ ] 架构图、ADR、数据模型、权限矩阵完成
[ ] 真实数据 PoC 跑通
[ ] 评测集 >= 50 题，基线与结果已记录
[ ] 压测覆盖 10/30/100 并发，P95 达标
[ ] 安全评审（权限/密钥/数据边界/依赖）通过
[ ] 部署包、运行手册、回滚手册齐备
[ ] Nginx/网关 SSE、超时、上传大小验证通过
[ ] 监控、告警、日志轮转上线
[ ] 回滚演练成功
[ ] 试点用户培训完成，反馈渠道建立
[ ] 7 天观察期无 P0/P1
[ ] 使用指标与复盘报告输出
```

## 常见反模式

- 先选技术再找问题；
- 把平台当架构，把低代码当能力；
- 只做 Demo，不做评测和压测；
- 权限靠前端隐藏，不靠后端强制；
- 没有回滚方案就上线；
- 把所有东西塞进一个进程，期望“以后再说”；
- 对外材料不脱敏。
